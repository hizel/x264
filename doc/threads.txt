Historical notes:
Slice-based threads was the original threading model of x264.  It was replaced with frame-based threads in r607.  This document was originally written at that time.  Slice-based threading was brought back (as an optional mode) in r1364 for low-latency encoding.  Furthermore, frame-based threading was modified significantly in r1246, with the addition of threaded lookahead.

Old threading method: slice-based
application calls x264
x264 runs B-adapt and ratecontrol (serial)
split frame into several slices, and spawn a thread for each slice
wait until all threads are done
deblock and hpel filter (serial)
return to application
In x264cli, there is one additional thread to decode the input.

New threading method: frame-based
application calls x264
x264 requests a frame from lookahead, which runs B-adapt and ratecontrol parallel to the current thread, separated by a buffer of size sync-lookahead
spawn a thread for this frame
thread runs encode, deblock, hpel filter
meanwhile x264 waits for the oldest thread to finish
return to application, but the rest of the threads continue running in the background
No additional threads are needed to decode the input, unless decoding is slower than slice+deblock+hpel, in which case an additional input thread would allow decoding in parallel.

Penalties for slice-based threading:
Each slice adds some bitrate (or equivalently reduces quality), for a variety of reasons: the slice header costs some bits, cabac contexts are reset, mvs and intra samples can't be predicted across the slice boundary.
In CBR mode, multiple slices encode simultaneously, thus increasing the maximum misprediction possible with VBV.
Some parts of the encoder are serial, so it doesn't scale well with lots of cpus.

Some numbers on penalties for slicing:
Tested at 720p with 45 slices (one per mb row) to maximize the total cost for easy measurement. Averaged over 4 movies at crf20 and crf30. Total cost: +30% bitrate at constant psnr.
I enabled the various components of slicing one at a time, and measured the portion of that cost they contribute:
    * 34% intra prediction
    * 25% redundant slice headers, nal headers, and rounding to whole bytes
    * 16% mv prediction
    * 16% reset cabac contexts
    * 6% deblocking between slices (you don't strictly have to turn this off just for standard compliance, but you do if you want to use slices for decoder multithreading)
    * 2% cabac neighbors (cbp, skip, etc)
The proportional cost of redundant headers should certainly depend on bitrate (since the header size is constant and everything else depends on bitrate). Deblocking should too (due to varying deblock strength).
But none of the proportions should depend strongly on the number of slices: some are triggered per slice while some are triggered per macroblock-that's-on-the-edge-of-a-slice, but as long as there's no more than 1 slice per row, the relative frequency of those two conditions is determined solely by the image width.


Penalties for frame-base threading:
To allow encoding of multiple frames in parallel, we have to ensure that any given macroblock uses motion vectors only from pieces of the reference frames that have been encoded already. This is usually not noticeable, but can matter for very fast upward motion.
We have to commit to one frame type before starting on the frame. Thus scenecut detection must run during the lowres pre-motion-estimation along with B-adapt, which makes it faster but less accurate than re-encoding the whole frame.
Ratecontrol gets delayed feedback, since it has to plan frame N before frame N-1 finishes.

PAFF (field pictures) and threads:
Under --paff, the two field passes of a complementary pair are coded as
two separate frame-thread jobs on consecutive slots (the slot rotation
advances by two per pair); the caller collects both jobs of the oldest
pair together (a rendezvous) before running the pair-level frame end.
Reference readiness is row-granular for BOTH fields: each pass produces
its parity's reference band (field-layout copy, hpel, borders) at row
cadence trailing the deblock, and dependent passes restrict their
vertical MV range to the completed field rows, exactly as progressive
frame threads do (thresholds in field lines; --non-deterministic keeps
the clamped range, the default deterministic mode uses the fixed
i_mv_range_thread).  A pair's second field waits on its own first field
by the same row rule.  The chain is therefore the per-pass diagonal
staircase of progressive threading; the old pair-job model (one job per
pair, first field gated on an intermediate-sweep phase) topped out at
~2x on P-chains.  N slots keep N/2 PAIRS in flight; pair jobs consume an
even slot count, so at an odd thread count the last slot idles.  Output
is deterministic at a fixed thread count, but not byte-identical to
--threads 1 (the MV-range clamp applies as in progressive).  This now
holds with VBV enabled too (see "Threaded VBV determinism" below).
Slice-based threading under PAFF is supported (paff-sliced-threads):
frame threading is off by construction (one pair in flight, monolithic
pair driver) and each field pass is split into N parity-interleaved
slice bands, one slice per band, coded in parallel.  Each thread
deblocks its own band rows at its slice end (cross-slice deblock off,
idc=2), and all reference-data work (field-layout copy, borders, hpel)
runs in a serial post-join sweep on the main context -- no cross-thread
pixel synchronization.  The thread count is capped at four field MB
rows per band (half the progressive cap: a field has half the frame's
MB rows).  Row-VBV budgets are per field: pass 0 gets the pair plan
scaled by its parity's SATD share, pass 1 the exact leftover floored at
5% of the pair plan.  Non-VBV modes (CRF/CQP/ABR) are byte-repeatable
at a fixed thread count; CBR+VBV inherits the sliced-threads timing
exception (below).  Measured on the same machine: 1.84x at N=2 and
3.21x at N=4 on 1080i; BD-rate overhead at or below the sliced-
progressive penalty at the same operating point (numbers in
doc/paff.txt).  See doc/paff.txt.

Threaded VBV determinism:
Historically, frame-threaded encoding with VBV enabled was NOT
byte-deterministic even at a fixed thread count: VBV decisions read live
state of frames still being coded by other workers (the per-row-updated
frame_size_estimated of in-flight slots at dispatch, and reference rows'
per-row QP/qscale/bits statistics during row-level ratecontrol), so the
output depended on worker timing.  This is fixed: dispatch-time planning
charges in-flight frames a deterministic estimate (planned size scaled by
the recent plan error of finished frames, plus an overshoot margin, both
tracked over harvested -- final -- frames only), and every reference-row
read is gated on a deterministic "row provably committed" check derived
from the frame-thread row-wait guarantee (see row_ref_committed in
encoder/ratecontrol.c for the derivation per coding mode: progressive
frame lines, MBAFF pair rows, PAFF per-parity field lines; PAFF
additionally keeps each field pass's row-bit accounting within its own
parity).  CBR+VBV output is now byte-identical across repeat runs at a
fixed thread count (verified at N = 2/4/8/16, with and without B-frames,
under --paff, and at 720p).  --threads 1 and the non-VBV ratecontrol
modes (CRF, CQP, ABR without VBV) are byte-identical before and after.
Slice-based threading is excepted: its cross-slice reads of live
bits_so_far / frame_size_estimated remain timing-dependent.  This
exception covers sliced PAFF equally (--paff --sliced-threads): CRF,
CQP and ABR-without-VBV stay byte-identical across repeat runs at a
fixed thread count (verified at N = 2/4/8 with and without B-frames),
while CBR+VBV output is timing-dependent and gated instead on Annex C
CPB compliance plus zero underflow warnings.

Measured consequences of the new threaded CBR+VBV trajectory (vs the old
nondeterministic one; tools/test_vbv_determinism.sh --quality):
- Long content (720p full length): bitrate error vs target unchanged
  (0.000%), PSNR-Y within 0.071 dB, SSIM within 0.00005; filler bytes up
  to +27% over the old median on one cell (more conservative planning
  pads more).
- Short clips (25-64 frames, i.e. startup-transient dominated): the old
  threaded runs overshot the target by 11-16% (by 32% under --paff); the
  new trajectory lands on or just under target, closer to --threads 1.
  Raw PSNR/SSIM on these cells drop commensurately with the bits no
  longer spent.
- Conformance (tools/check_hrd.py, --nal-hrd cbr): no CPB under/overflow
  in any post-change matrix cell; the old code itself underflows in ~1/12
  runs on the borderline scenecut cell (its determinism was luck).
  check_hrd.py reports a pre-existing end-of-stream finding ("removal
  time not increasing" on the last flushing AUs) on long --bframes 3
  streams, byte-identical before and after this change.
